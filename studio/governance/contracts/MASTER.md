# 第1部 用語の定義

ここに無い語は使わない。

| 語 | 定義 |
|---|---|
| **原画** | `art/references/user-provided/` にある22個のPNG。所有者が直接渡したもの |
| **派生** | 原画を切る・縮める・色を減らして作った新しいファイル |
| **ハッシュ値** | ファイルの中身から計算される64文字の英数字。中身が1バイトでも違えば必ず違う値になる。同じ値なら同じファイルだと言える。出し方は `shasum -a 256 <パス>` |
| **ドット** | 画像を構成する最小の四角。1ドット＝1色 |
| **絵のドット** | 絵を描いたときの最小の四角。画面に出すときは整数倍に拡大する |
| **タイル** | 地面を敷き詰める正方形。この案件では16ドット×16ドット |
| **セル** | キャラクター1コマ分の四角い領域。この案件では32ドット×32ドット |
| **足元の基準点** | セルの中で足の裏の中央が来る位置。左から16・上から30 |
| **シルエット** | 絵のうち透明でない部分の形だけを取り出したもの。色は無視する |
| **シルエット変化率** | 隣り合う2コマで `(片方だけにあるドット数) ÷ (どちらかにあるドット数) × 100`。単位は% |
| **頭身** | `図全体の高さ ÷ 頭のてっぺんから首までの高さ` |
| **色数** | その画像で使われている異なる色の個数。透明部分は数えない |
| **パレット** | 使ってよい色の一覧。この一覧に無い色を1ドットでも使ったら不合格 |
| **ランプ** | 同じ物の色を暗い順に並べたひとそろい |
| **量子化** | 画像の色を決められたパレットの色だけに置き換える処理 |
| **透明度** | ドットが透けているかどうかの値。0が完全透明、255が完全不透明 |
| **二値の透明度** | 透明度が0か255しかない状態。途中の値が1ドットでもあったら不合格 |
| **オートタイル** | 地面Aと地面Bの境目を自動で繋ぐための境目専用のタイル一式 |
| **47枚組** | オートタイルに必要な枚数。8方向が「自分と同じ地面か」を見ると意味のある組み合わせが47通りになる |
| **合格** | この文書に書かれた数値の範囲に入っていること。人の判断を挟まない |
| **不合格** | 範囲に入っていないこと。直してから次へ進む。**範囲を書き換えて合格にしてはいけない** |
| **Lv** | 住める街の段階。0から5まで。0＝設計図だけ、5＝見せたくなる街 |
| **区画** | 道で囲まれた領域。建物が入居する単位 |
| **種（seed）** | 街の骨格を決める値。リポジトリの同一性だけから作り、中身を含めない |

## 2. だから街は生成でなければならない

#### 理由1: 所有感
全員が同じ街なら、それは**サンプル**である。自分の街ではない。
街が自分のリポジトリの形をしているから、「俺の街」になる。

#### 理由2: 共有する意味
「スクショを撮って共有したくなる街」（07-11）は、**他人と違うから**成立する。
同じ街のスクショを100人が貼っても、誰も見ない。

#### 理由3: 成長が見える
リポジトリは育つ。街はその鏡である。
**鏡が固定なら、育ったことが映らない。** 第1章の23:40は永遠に来ない。

> **生成は機能ではない。生成が製品である。**

## 3. 三層分離 — 何が変わり、何が変わらないか

設計の核心。ここを間違えると、街は「毎回ちがう別の場所」になり、所有感が消える。

| 層 | 何 | 由来 | いつ変わるか |
|---|---|---|---|
| **L0 文法** | 語彙・住める判定・トーン・位相 | 設計 | 変わらない |
| **L1 素性** | 地形・水・街路網・区画の骨格・街の名前・気候 | **リポジトリの同一性** | **一生変わらない** |
| **L2 暮らし** | どの区画に何が建つ・建物の状態・人の数・時刻・汚れ | **リポジトリの中身** | **育つたびに変わる** |

### 3.1 L1 は「顔」である

人の顔は、太っても痩せても同じ顔である。街も同じ。

```
seed = SHA-256(リポジトリの同一性)     ← 中身を一切含めない
     → 気候 / 地形 / 川の走り / 街路網 / 区画の形 / 街の名前
```

**この契約はすでに実装されている。**
`src/town/world-identity.mjs:95-96`:
> Stable WorldPlan visual seed: SHA-256 of inspection.repository.name's exact UTF-8 bytes.
> **Repository contents never enter this seed.**

**これは資産である。壊してはいけない。**
（改善余地: 名前は変わりうる。origin URL か最初のコミットハッシュを優先し、無いときだけ名前に落ちる形が望ましい）

### 3.2 L2 は「暮らし」である

建物・住民・灯り・時刻は、リポジトリの今の姿から決まる。**毎回変わってよい。変わるべき。**

### 3.3 破ってはいけない一条 — 区画は先に全部つくる

23:40の体験を守るための、実装レベルの絶対条件。

```
❌ 悪い: 施設が5つなら5区画つくる → DBを足すと6区画になり、街が組み替わる
✅ 良い: seed から区画を全部つくる → 施設が5つなら5区画に入居、残りは更地
```

**空き区画は「更地」として最初から存在する。** だから DB を入れたとき、
**倉庫はもともとその区画にあった空き地に建つ。** 街は組み替わらない。**育つ。**

これが「街が育つ」と「街が作り直される」を分ける、たった一つの実装差である。

## 4. トポロジーは固定、ジオメトリは可変

前版の誤り: 「南＝外から来る側／北＝つくる側」と**方角を固定した**。それでは全員が同じ形の街になる。

正しい定式化:

> **意味の位相は不変。幾何は seed で変わる。**

### 4.1 5つの位相（不変）

| 位相 | 意味 | 入るもの |
|---|---|---|
| **入口域** | 外から人が来る | 城門・宿屋 |
| **生活域** | 今の暮らし・判定 | 広場・掲示板・井戸・住宅・商店 |
| **仕事域** | 自分がつくる | 役場・工房・道場・倉庫・見張り台 |
| **外縁域** | 外へつながる／配る | 酒場・接続者ギルド・港・船着場 |
| **過去域** | 歴史と汚れ | 廃屋・古民家・草むら・謎の路地 |

**位相の順序も不変**: 入口域 →(道)→ 生活域 →(境界)→ 仕事域。外縁域と過去域は生活域から分岐する。
だから**どんな街でも、歩けば構造が分かる**。

### 4.2 幾何は seed が決める（可変）

同じ位相順序を、まったく違う地形で実現する。

| 街タイプ | 位相の境界 | 見た目 |
|---|---|---|
| **川の街** | 川と橋 | 水が街を貫く。橋で仕事域へ渡る |
| **港町** | 岸壁と坂 | 外縁域が海に張り出す。船着場が主役 |
| **丘の街** | 崖と階段 | 仕事域が高台。見張り台が映える |
| **谷の街** | 尾根と切通し | 街が細長い。奥行きが出る |
| **平原の街** | 城壁と門 | 二重の壁。区画が広い |

**同じリポジトリは必ず同じタイプ。違うリポジトリは違うタイプ。**
これで「他人と違う街」と「歩けば分かる構造」が両立する。

### 4.3 街の名前

街には名前がある。名前がないものは自分のものにならない。

```
リポジトリ名 → 決定論的に和名を合成
  例: kantan → 「甘谷（かんたに）」 / codecity-inspector → 「古都見（ことみ）」
```
画面左上に **街の名前**、その下に小さく **リポジトリ名**。

## 5. 生成文法 — 毎回「美しい街」になる規則

08-02「美しい背景がマッピングされて生成される仕組み」への回答。
**美しさは偶然ではない。各工程に美しさの制約を置けば、どのseedでも成立する。**

生成は骨から作る。順序は逆にできない。

#### 工程1 気候・街タイプ（L1）
seed から5タイプの1つを選ぶ。同時にパレット変種（春・夏・秋・冬・霧）を選ぶ。
- **制約**: タイプとパレットの組合せは25通り。全通り目視承認済みのものだけ許可する

#### 工程2 地形（L1）
高低差2〜3段。水を1本。
- **制約A**: **水は必ずマップを貫通する。** 行き止まりの水は不自然で、一目で作り物に見える
- **制約B**: 高低差の境界は必ず**階段か坂で1箇所以上つながる**
- **制約C**: 平坦な領域が全体の50%以上（歩ける余白）

#### 工程3 街路網（L1）— ここが街の美しさの8割
- 幹線を1本（入口域から生活域へ）、そこから枝を3〜5本
- **制約A**: **直交格子にしない。** 道は2〜4タイルごとに1タイルずれる。SFCの街が美しいのはこの「揺らぎ」
- **制約B**: **行き止まりを1〜2本だけ作る。** これが「謎の路地」（07-11）になる。0本だと退屈、3本以上だと迷う
- **制約C**: **曲がり角には必ず何かを置く。** 井戸・大木・看板・街灯。何もない角は死んで見える
- **制約D**: 道幅は幹線3タイル、枝2タイル。均一にしない

#### 工程4 区画（L1）
道で囲まれた領域を区画とする。各区画に位相タグを付ける。**この時点で施設のことは考えない。**
- 入口に最も近い区画群 → 入口域
- 最大の広場を含む区画群 → 生活域
- 地形境界の向こう → 仕事域
- 水/端に接する区画 → 外縁域
- 最も遠い・最も高い区画 → 過去域
- **制約**: 各位相に最低2区画。総区画数は12〜20（少ないと寂しい、多いと散る）

#### 工程5 入居（L2）— ここで初めてリポジトリを見る
検出された施設を、位相の合う区画へ入居させる。**空き区画は更地のまま残す。**
- **制約A**: **建物は道に正面を向ける。** 背中や側面を道に向けない
- **制約B**: 同種の建物を隣り合わせない
- **制約C**: 背の高いもの（見張り台・役場）は奥、低いもの（井戸・住宅）は手前
- **制約D**: 重要施設は他の建物や木に隠れない（07-11 必須制約3）

#### 工程6 装飾（L1+L2）
- **制約A**: **空き地率 15〜30%。** これを外れたら再抽選。スカスカでも詰まりすぎでもない密度
- **制約B**: **画面のどこを切り取っても、必ず1つは目を引くものがある。** 1画面（20×15タイル）を全走査して確認する
- **制約C**: 汚れ（草むら・壊れた柵・古い張り紙）は**歩ける**。欠落は歩けない

#### 工程7 住民（L2）
代表NPCは施設の前、モブは道に。
- **制約**: 画面内に**常に1体以上の動くもの**がいる（人・鳥・猫・煙）

## 6. 役場検査 — どのseedでも成立することを機械で保証する

所有者は「LLMに毎回配置させない／generator と validator で再現可能にする」と決めた（07-11）。
`validateWorldPlan` は実装済み。**そこに美しさの検査を足す。**

| 検査 | 合格条件 | 落ちたら |
|---|---|---|
| 歩ける | 入口域から全位相へ経路がある | 再生成 |
| 見える | 重要施設が遮蔽率20%以下 | 配置やり直し |
| 密度 | 空き地率 15〜30% | 装飾を増減 |
| 揺らぎ | 直線道路の最長が8タイル以下 | 街路やり直し |
| 焦点 | 全1画面切り取りに注目物が1つ以上 | 装飾追加 |
| **安定** | **同じ seed・違うコンテンツで、地形/道/区画が完全一致** | **バグ。最優先で直す** |
| 再現 | 同じ入力で常にバイト一致 | バグ |

**「安定」検査が最重要。** これが壊れると第1章の23:40が壊れ、製品価値が消える。

### 6.1 生成時間もエンドカスタマー体験である

`npx codecity` を叩いた人は待たない。
現在、500ファイルの生成＋検証に **9.7秒**（テスト失敗中、上限3秒）。1000ファイルで9.2秒。

**これは性能テストの不合格ではなく、体験の不合格である。**
14:03に街が立ち上がらなければ、14:04も23:40も来ない。目標は**2秒以内**。

## 7. 街が育つ瞬間の演出

23:40 のための演出。**これが無いと、育ったことに気づかれない。**

```
1. 前回の判定を保存しておく（localStorage）
2. 再訪時、差分があれば街に入る前に一言だけ
       「留守のあいだに、街が変わったようです」
3. 城門をくぐると、変わった場所に**光の柱が1本**立っている（控えめに）
4. 歩いて近づくと消える
5. 新しく建った施設の住民が、その場で一言
       台帳係：「倉庫、建ちました。もう消えません。」
```

**ファンファーレを鳴らさない。** 静かな方が強い。

**減った場合も同じ規律で扱う。** 責めない。
```
書記：「見張り台の灯りが、消えていました。」
```

## 8. トーン — この街はエンドカスタマーを責めない

「街は汚れていてよい」と「このままだと誰も住めません！」を両立させる唯一のトーン。

> **「誰も住めません」は批判ではなく悲鳴。**
> エンドカスタマーは**査定される被告ではなく、頼られる領主**である。

- 判定を出すのは数値ではなく**人**
- 「〜がありません」ではなく「**〜がなくて、困っています**」
- 欠落は赤い×ではなく、**灯りのない窓・更地・渡れない橋**
- 直ると**灯りがひとつ増える**

**この一条に反するUI・台詞・エフェクトは全部不採用。**

### 8.1 住民の声（表を出さない実装）

| 住人 | 条件 | 台詞 |
|---|---|---|
| 台帳係 | DB なし | 「書いても、朝には消えてるんです」 |
| 井戸番 | env なし | 「水の出どころが分からなくて、飲ませられません」 |
| 見張り台の番人 | logs なし | 「夜に何かあっても、朝まで誰も知らないんですよ」 |
| 検査官 | test なし | 「検査したいんですがね。台がないんです」 |
| 修理屋 | rollback なし | 「壊れたら、もう戻せません」 |
| 酒場の主人 | コスト制御なし | 「樽がね、勝手に減っていくんです」 |
| 旅人 | 公開入口なし | 「門、開かないんですけど……」 |

全員が**状況**を嘆いている。誰もエンドカスタマーを責めない。

### 8.2 会話の分量規律

07-15「文字も小さく、内容も高度すぎて意味不明」への回答。

- 技術名は**ギルド名簿の中だけ**
- 1人のNPCは**1件だけ**言う

## 9. 門の外の男

所有者が4回書いた思想を、説教ではなく一枚の絵にする。**街タイプが変わっても、門は必ずある。**

```
代理人：「完成しました。修正しました。テストしました。」
門番　：「役場の検査印がありません。お通しできません。」

- 代理人は嘘つきでも悪役でもない。**淡々と正しいことを言い続けるのが一番怖い**
- そしてこの街を建てたのは、他ならぬその工務店である

## 14. 判断に迷ったときの5条

## 1. 体験

### 1.1 顧客は3人いる

| | A 作りたい人 | B 作っている人 | C 作らせた人 |
|---|---|---|---|
| 状態 | リポジトリがほぼ空 | 動く物がある | LLMに書かせた。中身を知らない |

| 離脱する理由 | 墓場を見せられた | 知っていることしか出ない | 専門語で分からない |
| 2026年の人数 | 多い | 中 | 最多 |

**Lv.0 に警告を出さない。** まだ誰も住もうとしていない。
Lv.0 の画面は朝もやの高原・測量杭・天幕・焚き火・測量士1人。地形と道は既に見えている。

```

### 1.2 街には性格がある

宿屋（公開Web）を全員に要求すると、ライブラリやCLIの作者は永久に不合格になる。これは誤診。

| 性格 | 対象 | 中心施設 | 宿屋 |
|---|---|---|---|
| 宿場町 | 公開Webサービス | 宿屋 | 必要 |
| 工房町 | ライブラリ・SDK | 工房・道場 | **不要** |
| 港町 | CLI・モバイル・パッケージ | 船着場 | 不要 |
| 哨戒所 | bot・cron・worker | 見張り台 | 不要 |
| 研究村 | 実験・個人用 | 工房・草むら | 不要 |

**不要な施設は更地すら描かない。** 存在しない期待を街に置かない。

### 1.3 全長9段

| 段 | いつ | 何が起きるか |
|---|---|---|
| P0 出会う | 画面の前に座る前 | 他人の街のスクリーンショットを見る。約束は1行「あなたのリポジトリが、街になります」 |
| P1 起動 | 0〜3秒 | ターミナルに測量の進み具合が街の言葉で出る |
| P2 最初の10秒 | 0〜2.8秒 | 街が建つところを見る（§9.2） |
| P3 最初の1分 | 〜60秒 | 立つ・歩く・語彙を受け取る |
| P4 散歩 | 3〜10分 | 街を歩く。光る場所は常に1つだけ |
| P5 検査報告 | 〜1分 | 悪い知らせを受け取る |
| P6 去り際 | 数秒 | 門番が「またおいで」。ターミナルに1行残る |
| P7 再訪 | 次の日 | **前に空き地だった所に倉庫が建っている** |
| P8 習慣と誇り | 以後 | 街の絵を人に見せる |

### 1.4 P7 が成立する実装条件

```
悪い: 施設が5つなら5区画つくる → DBを足すと6区画になり街が組み替わる
良い: 街の骨格から区画を全部つくる → 5つ入居、残りは更地のまま
```

**空き区画が最初から更地として存在する。** これが「街が育つ」と「街が作り直される」を分ける唯一の実装差。

## 5. タイポグラフィ

### 5.1 大きさ

| 用途 | 全角 | 半角 | 行間 |
|---|---|---|---|
| 本文（会話・札） | 12ドット | 6ドット | 4ドット |
| 名前・地名・見出し | 10ドット | 5ドット | 3ドット |
| 補足（リポジトリ名） | 8ドット | 4ドット | — |
| 数字（等幅） | 8×12ドット | — | — |

### 5.2 組みの決まり

- **1行は全角20字まで。2行まで。** 超えたら次の送りに分ける
- **改行は手で入れる。** 自動の折り返しに任せない
- **行頭に置かない**: `。 、 」 ） ！ ？ ・ ー`
- **行末に置かない**: `「 （`
- **ルビを振らない。** 難しい漢字を使わないことで解決する
- **英数字と和文の間に半角の空きを1つ入れる**
- **数字は3桁ごとの区切りを入れない**（街の中では数を語らないので出番が無い）

### 5.3 文字の絵

| 項目 | 値 |
|---|---|
| 収録 | ひらがな全部・カタカナ全部・常用漢字1,200字・英数記号 |
| 作り | 全角12×12ドット、半角6×12ドット |
| 縁 | アンチエイリアスを使わない。透明度は0か255だけ |
| 未収録の字 | 豆腐を出さない。**かなに開く** |
| 使用許諾 | 再配布してよいもの。`THIRD_PARTY_NOTICES.md` に書く |

### 5.4 文字と背景

**合格の境界**: 明るさの比が **4.5倍以上**。
`ink #12141C` と `paper #F4EEDC` の組み合わせで13倍あるので、この2色を使えば必ず通る。

## 7. カラー

### 7.1 パレット

`studio/art-department/authority/palette-v1.json` に56色。
14の系統（石・土・草・葉・木・水・赤屋根・青屋根・肌・暖布・寒布・金・灯り・空）を、暗い順に3〜5段ずつ。

> **v1 は仮版である。** 原画22点を精読する前に理論で組んだもの。第8部 工程2 に従い、原画から再抽出して v2 に置き換える。検査G1（パレット外0ドット）はその時点の最新版で判定する。
加えて `ink #12141C`（輪郭）と `paper #F4EEDC`（最も明るい）。

**全アセットはこの中の色しか使えない。1ドットでも外れたら不合格。**

### 7.2 暗い側と明るい側の作り方

```
暗くする   色味を青や紫の方へ回す ＋ 鮮やかさを上げる ＋ 明るさを下げる
明るくする 色味を黄や橙の方へ回す ＋ 鮮やかさを下げる ＋ 明るさを上げる
```
灰色を混ぜない。混ぜると濁る。

例（石）: 暗部は色味225度（青寄り）→ 明部は40度（黄寄り）。

### 7.3 使わない色

- 真っ黒（0,0,0）… 画面から浮く。輪郭には `ink` を使う
- 真っ白（255,255,255）… 最も明るい所には `paper` を使う

### 7.4 地面の明るさ

**隣り合う地面タイルの明るさの平均の差は8以下。**（明るさは0〜255）
原画15番の石畳5種はこれを守っている。守らないと人物が地面に埋もれる。

### 7.5 人物と地面の分離

人物の明るさの中央値と、立っている地面の明るさの中央値の差が **25以上**。
足りないときは人物の主色を1段明るくするか、接地影を1段濃くする。

### 7.6 時刻6段階は色を1枚重ねるだけ

| Lv | 時刻 | 重ねる色 | 合成 | 濃さ |
|---|---|---|---|---|
| 0 | 朝もや | 空[3] | 通常 | 22% |
| 1 | 明け方 | 空[1] | 乗算 | 30% |
| 2 | 朝 | 空[4] | 通常 | 10% |
| 3 | 昼 | — | — | 0% |
| 4 | 夕方 | 赤屋根[3] | 乗算 | 18% |
| 5 | 黄昏 | 金[0]→青屋根[0] の縦のぼかし | 乗算 | 28% |

窓の灯りは加算で乗せ、Lv.3以降で点く。**タイルは描き直さない。**

### 7.7 気候5種も色の差し替えだけ

温帯（既定）／乾燥（土を強く・草を弱く）／寒冷（空を青へ・石を強く）／湿潤（葉を濃く・水を強く）／霧（全体に空[2]を12%）
**タイルは1組しか描かない。**

## 8. モーション

### 8.1 使う曲線は3つだけ

```
OUT  1-(1-t)²        出だし速く、着地やわらかい（既定）
IO   t<.5?2t²:1-2(1-t)²   往復・カメラ
LIN  t               点滅など等速でよいもの
```

### 8.2 走りが既定である理由

原画1番の歩き6コマを4方向で測った結果:

| 向き | シルエット変化率の平均 | 最小 | 頭のてっぺんの上下 |
|---|---|---|---|
| 南 | 22.0% | 10.2% | 身長の3.7% |
| 東 | 15.3% | 7.5% | 3.7% |
| 西 | 13.7% | **3.0%** | 7.0% |
| 北 | 18.5% | 8.0% | 4.3% |

最小3.0%は、隣り合う2コマがほぼ同じ形だということ。動いて見えない。
歩きは常にどちらかの足が地面に着いているので、形の変化幅が構造的に取れない。
走りは両足が地面から離れるコマがあるので取れる。

**よってプレイヤーの既定を走りにする。**

### 8.3 走りの6コマ

| コマ | 名前 | 体の上下 | 内容 |
|---|---|---|---|
| 1 | 接地・右 | 0 | 前後の足の開きが最大 |
| 2 | 沈み | +2（下げる） | 体が一番低い |
| 3 | 跳ね | −3（上げる） | **両足が地面から離れる**。一番高い |
| 4 | 接地・左 | 0 | 1の左右入れ替え |
| 5 | 沈み | +2 | |
| 6 | 跳ね | −3 | |

```
1コマ66.7ミリ秒 / 1周期400ミリ秒 / 1秒75ドット / 1歩15ドット / 1コマで5ドット進む
前傾: 頭を足より2〜3ドット前へ
```

**合格の境界**: シルエット変化率25〜45%、同じ形のコマ0組、頭の上下が身長の10%以上、地面から離れるコマが2、接地コマの足を1コマにつき5ドット後ろへずらす。

# 第7部 顧客体験の全長（詳細）

**対象**: エンドカスタマー（自分の小規模サービスを作っている／作りたい開発者）が、この製品と出会ってから習慣にするまでの全行程。
**原則**: 一つの山場を設計するのではない。**始まりから、離脱の可能性まで、全部設計する。**

---

## 1. エンドカスタマーは3人いる

一人だと思って設計すると、必ず誰かを殺す。

| | **A 作りたい人** | **B 作っている人** | **C 作らせた人** |
|---|---|---|---|
| 状態 | リポジトリはほぼ空 | 実物がある。動いている | LLMに書かせた。中身を把握していない |
| 判定 | **Lv.0〜1** | Lv.2〜3 | Lv.1〜3（穴だらけ） |
| 恐れ | 「何もない自分」を突きつけられる | 見落としがあること | 何が入っているか分からない不安 |
| 欲しいもの | **希望と最初の一歩** | 抜け漏れの発見 | **中身の可視化** |
| 離脱理由 | 「墓場を見せられた」 | 「知ってることしか出ない」 | 「専門用語で分からない」 |
| 2026年の人口 | 多い | 中 | **最多** |

### 1.1 私が犯していた設計ミス

前版で Lv.0 を「灯り0・人0・風だけ」と書いた。
**これは A に墓場を見せる設計であり、最大の見込み客を接触1分で殺す。**

> **修正: Lv.0 は死んだ街ではない。「これから建つ土地」である。**

```
Lv.0 の画面：
  夜明け前ではなく、朝もやの高原。
  測量杭が数本。天幕がひとつ。焚き火。測量士がひとり。
  地形と川と道はもう見えている（L1はリポジトリ名だけで確定するから）。
  ただ建物がまだ無い。

  測量士：「いい土地ですよ。水もある。あとは建てるだけです。」
```

**Lv.0 は美しくなければならない。** ここで「うわ、いいな」と思わせるのが A の獲得点。
判定文言も変える。Lv.0 では「誰も住めません」を**出さない**。まだ誰も住もうとしていないから。

```
Lv.0  「まだ、誰も来ていません。」      ← 期待
Lv.1  「明かりがひとつ、つきました。」  ← 承認
Lv.2〜「このままだと誰も住めません！」  ← 初めて警告が出る
```

**警告は、住もうとしている人がいて初めて意味を持つ。**

## 2. 街には性格がある — 全員がWebサービスではない

もう一つの設計ミス。宿屋＝公開Webを前提にすると、**ライブラリやCLIの作者は永久に「誰も住めません」と言われ続ける**。これは誤診であり侮辱である。

> **リポジトリの種類を先に判定し、街の性格と住める条件を切り替える。**

| 街の性格 | 対象 | 中心施設 | 「住める」の条件 | 宿屋 |
|---|---|---|---|---|
| **宿場町** | 公開Webサービス | 宿屋 | 入口・DB・env・ログ・検査・復旧 | 必須 |
| **工房町** | ライブラリ / SDK | 工房・道場 | ビルド・検査・版・出荷・文書 | **無くてよい** |
| **港町** | CLI / モバイル / パッケージ | 船着場・造船所 | 出荷経路・版・署名・検査 | 無くてよい |
| **哨戒所** | bot / cron / worker | 見張り台・工房 | 起動・ログ・復旧・費用制御 | 無くてよい |
| **研究村** | 実験 / 個人用 | 工房・草むら | **ほぼ何も要求しない** | 無くてよい |

判定は `detect.mjs` の既存シグナル（package.json の bin / main / exports、CI、Dockerfile、公開ポート等）で機械的に決まる。

**工房町に宿屋が無いのは欠落ではない。** そこに更地すら描かない。**存在しない期待は、街に描かない。**
そして街の性格は画面に一言だけ出す。

```
古都見 ── 工房のまち
```

## 3. 体験の全長（9フェーズ）

```
P0 出会う   → P1 起動 → P2 最初の10秒 → P3 最初の1分 → P4 散歩(3〜10分)
            → P5 掲示板 → P6 去り際 → P7 再訪 → P8 習慣と誇り

### P0 — 出会う（画面の前に座る前）

**接触点**: GitHub README / SNSに貼られた誰かの街のスクショ / `npx` の一行。

**設計するもの**:
- **最初に見せるのは機能説明ではなく、他人の街のスクショ**。「これが俺のリポジトリ」というキャプションつき
- 一行の約束：**「あなたのリポジトリが、街になります。」** それ以上言わない
- インストール手順は**1行だけ**。`npx codecity`
- 「診断」「解析」「スコア」という語をどこにも使わない（原則2）

**離脱の防ぎ方**: 「何ができるの？」に答えようとすると長くなる。**街の絵1枚と1コマンドだけ**にする。

### P1 — 起動（ターミナル）

```
$ npx codecity

  古都見（ことみ）を測量しています…

  ✓ 水の道を引いた        env / config

  ✓ 建物を建てた          9 施設
  ✓ 住民を呼んだ          23 人

  http://127.0.0.1:4173  でお待ちしています。
```

**設計判断**:
- **ここで既に街の名前を出す**。所有感は最初の1行から始まる
- 進捗を「解析」ではなく**街の言葉**で出す。ターミナルもゲームの一部
- **リポジトリの中身を1バイトも送らない**ことを、最後に1行で明示する
  ```
  （このツールはコードを外部に送信しません）
  ```
  Cの不安（何が入っているか分からない）に効く最初の一手
- ブラウザは**自動で開く**。`--no-open` で止められる

### P2 — 最初の10秒（画面）

**ここが製品の生死を分ける。** 何も理解していない人が最初に見るもの。

#### 設計: 生成そのものを見せる

ローディング画面を「待たせる時間」ではなく**「街が建つのを見る時間」**にする。

```
0.0s  暗転。中央に街の名前が浮かぶ    古都見
0.3s  地形が現れる（等高線が引かれるように、外周から）
0.8s  水が流れ込む（実際に上流から下流へアニメーションする）
1.2s  街道が伸びる（幹線→枝の順に、線が引かれるように）
1.6s  区画が光る（14区画が順に、0.02秒ずつずれて）
2.0s  建物が建つ（下から せり上がる。9施設が順に）
2.4s  灯りがつく。住民が湧く
2.8s  カメラが城門へ寄る。ゲーム開始
```

**これが「あなたのリポジトリから作られた」ことを、説明ゼロで伝える。**
そして2.8秒は「待った」ではなく「見た」になる。

**性能要件はここから決まる**: 生成は**2秒以内**（現在1000ファイルで9.2秒。体験の不合格）。
2秒を超える場合、演出を引き伸ばさず**測量士が「もう少しかかります」と言う**。嘘をつかない。

#### 最初のフレームで出す情報は3つだけ

```
左上   古都見 ── 工房のまち
中央   キャラクターが城門の前に立っている
下部   （3秒だけ）矢印キーで歩けます
```

Lv・スコア・ファイル数・依存グラフ、**何も出さない**。

### P3 — 最初の1分（立つ・歩く・分かる）

#### 操作の学習（チュートリアル画面を作らない）

| 秒 | 起きること | 学ぶこと |
|---|---|---|
| 0〜3 | 下部に `矢印キー / WASD で歩けます` が3秒だけ出て消える | 移動 |
| 3〜10 | 動かないと、**門番が「入るのかい？」と手招きする** | 進む方向 |
| 10〜20 | 門をくぐると `Enter で調べる・話す` が3秒 | 決定 |
| 20〜40 | 最初のNPC（宿帳係 or 測量士）が**向こうから話しかけてくる** | 会話 |
| 40〜60 | そのNPCが「広場の掲示板を見てくるといい」と言う | 目的 |

**チュートリアルウィンドウを1枚も出さない。** 全部、街の中の出来事として起きる。

#### 最初の会話で「語彙」を渡す

宿屋＝公開Webという対応は、説明しないと分からない。**が、説明表を出さない。**

宿帳係：「うちは宿屋だ。外から来た人が
　　　　　最初に寄る場所さ。」

　　　　　入口ってことだね。」
```

**1回だけ、1人だけが、括弧つきで教える。** 以後どのNPCも技術語を言わない。

### P4 — 最初の散歩（3〜10分）

#### 発見の順序を設計する（自由だが導線はある）

```
城門 → 宿屋（入口の状態）→ 広場（掲示板が光っている）
                         ├→ 東：酒場（つながり）
                         ├→ 奥：仕事域（工房・道場・倉庫・見張り台）
                         └→ 端：過去域（廃屋・草むら）
```

- **光る対象は同時に1つだけ。** 次に行くべき場所だけが、ごく弱く明滅する
- **順序は強制しない。** どこへ行ってもよい。ただし迷ったら光る場所がある
- **行き止まりの路地には必ず何か置く。** 空の行き止まりは事故に見える

#### 歩くこと自体を楽しくする（07-11「歩いているだけで楽しい街」）

| 仕掛け | 頻度 | 内容 |
|---|---|---|
| 生活音 | 常時 | 鍛冶の音、水音、遠くの話し声。位置で音量が変わる |
| 動くもの | 常時 | 画面内に必ず1つ以上（鳥・猫・煙・旗・洗濯物） |
| すれ違い | 20〜40秒に1回 | モブが横切る。ぶつからない |
| 独り言 | 話しかけると | モブは1人1言。天気か仕事の話。技術の話はしない |
| 小さな発見 | 区画に1つ | 井戸を調べると硬貨、木箱に猫、看板に落書き |

**報酬は出さない。** 見つけたこと自体が報酬。ポイントもトロフィーも作らない。

#### 歩きたくない人のための道（重要）

「答えが早く欲しい」人は必ずいる。**追い返してはいけない。**

- `M` または画面右下の小さなボタンで **街を見渡す**（ズームアウト＋施設名の表示）
- そこから施設をクリックすると**その場へ瞬間移動**
- 掲示板は最初から見渡し画面に表示され、**クリックで判定全文が読める**

**ダッシュボードは作らない。** ただし**歩かずに掲示板へ行く自由**は必ず残す。これは原則2に反しない——情報は依然として街の中にある。

### P5 — 掲示板（痛みをやさしく渡す）

**この製品で唯一、悪い知らせを渡す場面。** 設計を一番丁寧にする。

```
1. 掲示板に近づくと、書記が奥から歩いてくる（走らない）
2. 住民が2〜5人、自然に集まる。誰もプレイヤーを見ない
3. 書記が札を1枚ずつ貼る（0.4秒間隔、1枚 = 1事実）
4. 貼るたび、その施設の方向を住民の誰かが見る
5. 最後に判定札
6. **プレイヤーはいつでも離れられる。** 拘束しない
```

#### 札の文型（不変）

```
   〈あるもの〉はあります。
   しかし、〈足りないこと〉。
```

**必ず「ある」から始める。** これが「責めない」の文法的実装。

#### 判定札は段階で変わる

| Lv | 札 |
|---|---|
| 0 | `まだ、誰も来ていません。` |
| 1 | `明かりがひとつ、つきました。` |
| 2 | `このままだと誰も住めません！` |
| 3 | `人が住めます。` |
| 4 | `にぎわっています。` |
| 5 | `見せたくなる街です。` |

#### 直後に必ず「次の一歩」を渡す

診断だけで放り出さない。書記が最後に一言。

```
書記：「まずは倉庫でしょうね。
　　　　台帳係が、ずっと待っています。」
```

**やるべきことを1つだけ言う。** リストにしない。

### P6 — 去り際（設計されていなかった領域）

人は必ず離れる。**去り際が次の再訪を決める。**

#### 去り方は3つ。全部設計する。

| 去り方 | 起きること |
|---|---|
| **ブラウザを閉じる** | 何もしない。次回は同じ場所から再開（`persistence.mjs` は実装済み） |
| **`Esc` を押す** | 「街を離れますか」ではなく **「またおいで」** と門番が言い、城門の外へ。スクショボタンが出る |
| **ターミナルで Ctrl+C** | ターミナルに最後の1行を残す |

#### ターミナルに残す最後の1行（再訪トリガー）

```
  古都見 Lv.2 ── 倉庫が空き地のままです。
  また `npx codecity` で見に来てください。
```

**これが唯一のリテンション施策である。** 通知もメールもアカウントも作らない。
ターミナルに残った1行が、次に `npm run dev` を叩いたとき目に入る。

### P7 — 再訪（育ちの体験）

```
1. 起動。P1 の測量ログが流れる
2. 前回と差分があれば、ターミナルに1行
       街が変わったようです。
3. ローディング演出は**差分だけハイライト**して建つ
4. 城門をくぐると、変わった場所に **光の柱が1本**（控えめ）
5. 近づくと消え、その施設の住民が一言

       台帳係：「倉庫、建ちました。もう消えません。」
```

#### これが成立する実装条件（`WORLD-DESIGN.md` §3.3）

**空き区画は最初から更地として存在する。** だから倉庫は「前に空き地だった、あの場所」に建つ。
街は組み替わらない。**育つ。**

#### 減ったときも同じ規律

```
書記：「見張り台の灯りが、消えていました。」
```
責めない。事実だけ。

### P8 — 習慣と誇り

#### 習慣にする仕掛け（1つだけ）

`package.json` に1行足すだけの提案を、Lv.3 到達時に一度だけ出す。

```
"scripts": { "town": "codecity" }
```

**それ以上の統合（CI、bot、Slack通知）は提案しない。** 押し付けは離脱を生む。

**Lv.5 限定にしない。** これも設計ミスだった。A（作りたい人）は Lv.5 に来ない。

| Lv | 書き出せるもの | キャプション例 |
|---|---|---|
| 0 | 朝もやの測量地 | `ここに街を建てます` |
| 1 | 最初の灯り | `明かりがひとつ、つきました` |
| 2〜3 | 昼の街 | `人が住めるようになりました` |
| 4 | 夕方のにぎわい | `にぎわっています` |
| **5** | **黄昏の全景** | `見せたくなる街です` |

**どの段階でも貼れる。** 貼る動機は達成ではなく**「自分の街を見せたい」**であり、それは Lv.0 でも起きる。

書き出し仕様は `CX-04` に記す。

## 4. 感情曲線

```
期待 ─┐                                         ┌─ 誇り
      │  驚き ─┐                        ┌─ 達成 ┘
      │        │  迷い ─┐        ┌─ 意欲 ┘
      │        │        └─ 理解 ─┤
      │        │                  └─ 痛み（やさしい）
   P0 │  P1-P2 │  P3     P4        P5        P7      P8
```

**設計上の要点**:
- **痛み（P5）の前に、必ず愛着（P4）を作る。** 順序が逆だと反発になる
- **痛みの直後に必ず「次の一歩」**（P5末尾）。放置は無力感になる
- **達成（P7）は静かに。** 大きく祝うと、次に何も起きないときの落差が大きい

## 2. 原画が確定させていないもの（ここだけ設計が要る）

### 2.1 コマ割り ← 最大の問題

**出典**: `character_style_authority_20260722_v1.png` の3〜8列目（歩行6コマ）を4行すべてで実測した。

| 向き | シルエット変化 平均 | 最小 | 頭頂の上下 |
|---|---|---|---|
| 南（前） | 22.0% | 10.2% | 7px / 187px = 3.7% |
| 東（側） | 15.3% | 7.5% | 3.7% |
| 西（側） | **13.7%** | **3.0%** | 7.0% |
| 北（後） | 18.5% | 8.0% | 4.3% |

**最小3.0% = ほぼ同一のコマが隣り合っている。** 頭頂の上下は身長の4〜7%。

> **絵は最高品質だが、コマ割りは弱い。**
> 所有者の「あれコマ割りで最悪で歩かせたら最悪だった」は、数値で裏づけられる。

**したがって原画のコマ割りは継承しない。**（絵柄・配色・顔・プロポーションは継承する）

### 2.2 既定を「走り」にする理由

歩きは構造的に silhouette の変化幅が取れない。走りは取れる。

| | 歩き | 走り |
|---|---|---|
| 定義 | 常にどちらかの足が接地 | **両足が地面から離れるコマがある** |
| シルエット変化 | 原画実測 13〜22% | 設計値 **25〜43%** |
| 頭頂の上下 | 原画実測 4〜7% | 設計値 **14%** |
| 前傾 | なし | 2〜3px |

**プレイヤーの既定を走りにする。** 歩きはNPCと室内だけに使う。
「歩いているだけで楽しい街」は「走っているだけで気持ちいい街」になる。それでよい。

#### 走りの6コマ（キーポーズ）

| # | ポーズ | 体の上下 | 内容 |
|---|---|---|---|
| 1 | 接地R | ±0 | 前足が着く。最も歩幅が広い＝**情報量が最大のコマ** |
| 2 | 沈み | **+2** | 前足に体重。最も低い |
| 3 | 跳ね | **−3** | **両足が地面から離れる**。最も高い |
| 4 | 接地L | ±0 | 1の脚を入れ替え |
| 5 | 沈み | +2 | |
| 6 | 跳ね | −3 | |

```
1コマ 66.7ms（60fpsで4フレーム） / 周期400ms / 速度75px秒 / 歩幅15px
1コマあたりの移動 5px  ← 接地中の足はスクリーン上で5px後退させる（足が擦らない条件）
```

**作画枚数**: 脚組3ポーズ × 3方向（西は東の反転）＝ **9組**。胴と頭は方向ごとに1枚。

### 2.3 作画3原則（これを外すと必ず滑る）

1. **シルエット変化率を帯に入れる。** 走り 25〜45% / 歩き 20〜30%。**同一コマ（0%）は禁止**
2. **頭頂を身長の10%以上、上下に動かす。** ここが数%だと、何コマ描いても滑る
3. **接地コマの足をワールド座標に固定する。** 1コマの移動量ぶん、足を後退させる

### 2.4 その他、原画に無いもの

# 第9部 アセット総目録・抽出ガイド・再生成ガイド

**手順2へ戻ってはいけない理由**: 生成し直すと絵柄が変わる。7月に絵柄がずれたのはこれが原因。

### 2.2 指示文の型

画像生成へ渡す指示は、次の6つを必ず含める。欠けると絵柄がずれる。

```
1  何を描くか        : 「石造りの二階建ての宿屋、正面に木の扉、両脇に灯りの入った窓」
2  視点             : 「斜め上から見下ろす。屋根の面・正面の壁・左側面の3面が見える」
3  光               : 「光は左上から。右下に影が落ちる」
4  色               : 「屋根は青灰、壁は生成りの漆喰と焦茶の柱、基壇は灰の石積み、窓は橙に光る」
5  作り             : 「下から石積みの基壇、壁、屋根の3段。瓦は横方向の段で描く。縦線は入れない」
6  してはいけないこと : 「網点を使わない。真っ黒を使わない。半透明を使わない。文字を入れない。
                       背景は一色の単色にする」
```

**5番は原画から読み取った作りをそのまま書く。** ここを省くと別の建物になる。

### 0.4 根本原因 — 契約が「ドット絵かどうか」を一度も検査していない

現行の素材契約が縛っているのは3つだけ:

```
640×512 / 4行×10列の40セル / 各64×128 / 足元pivot (32,120) / alpha は厳密に {0,255}
```
（これは旧契約の記録。新契約は第11部§1.1 の 192×256 / 48セル。）

**寸法・pivot・alpha。この3つはドット絵とは何の関係もない。**

> **本教本の中心的な処方は「パレット契約」である。**
> 画風は目で守るものではない。**パレット外の色が1pxでもあったら不合格**という機械ゲートで守る。
> そうすれば、誰が・どの生成器で作っても、絵柄は原理的にブレない。

## 第1章 SFC後期RPGが美しい理由 — 5つの統一

ロマサガ3・FF6・聖剣伝説3が今も美しいのは、絵が上手いからではない。**5つが統一されているから**である。ひとつでも崩れると、目は即座に「作り物」と判定する。

#### 統一1: ピクセル単位（art pixel）
画面上のすべてが**同じ大きさの正方形**でできている。背景だけ細かい、キャラだけ粗い、が起きない。
→ 現状: 背景は1px単位の絵画、キャラは実質1px単位の絵画。単位は揃っているが、**どちらも「打たれたドット」ではない**。

#### 統一2: パレット
全素材が**同じ色見本**から取る。空の青と、屋根の青と、服の青が同じ色番号を共有する。これが「同じ世界の物である」という感覚を作る。
→ 現状: 共有パレットが存在しない。206,254色。

#### 統一3: 光源
光の来る方向が**全素材で1つ**。SFCの定番は**左上から**。だから影は右下に落ち、ハイライトは左上に乗る。
→ 現状: 背景は環境光ベースの柔らかい陰影、キャラは正面からの均一光。方向が一致していない。

#### 統一4: 投影角（斜め見下ろし）
背景が「上から30〜45度見下ろした角度」で描かれているなら、**キャラも同じ角度で描く**。具体的には:
- 頭のてっぺんが少し見える
- 肩の上面が見える
- 足は手前に短縮される（フォアショートニング）
→ 現状: 背景は屋根の側面・井戸の側壁が見える明確な斜め見下ろし。**キャラはほぼ真正面立ち**。この角度差が「貼り付けたステッカー」感の正体。07-15「斜め見下ろしのビューにしたい」への未回答部分はここ。

#### 統一5: 接地
すべての立体が**地面のどこに立っているか**を、影で明示する。影の縦横比は投影角と一致する。
→ 現状: 影は実装済み（11:4 ≒ 縦横比0.36）。ただし背景の投影角と一致しているかは未検証。**影の縦横比 = cos(見下ろし角) にする**。

## 第2章 「効率よくブレないフレーム」の作り方

07-22「絵柄がブレることは許容されない」/ 08-02「違和感のないドット絵のフレームをどうやれば効率よく生成できるか」への回答。

### 2.1 大原則: フレームを生成してはいけない

**歩行8コマを8回生成すると、8回とも絵柄が違う。** これが7月に起きたことのすべて。
プロの制作は逆で、**1枚だけ描いて、残りは決定論的に作る**。

```
マスターポーズ 1枚（南向き・静止）
   ↓ 手で描く / 生成 → 規約通過まで直す
   ↓
   ├─ 歩行4コマ  ← マスターの脚と腕だけを差し替える（胴・頭は1pxも動かさない）
   ├─ 東向き     ← 別途1枚だけ描く
   ├─ 西向き     ← 東向きの左右反転（自動）
   └─ 北向き     ← 別途1枚だけ描く（後頭部）
```

生成回数は **8回 → 3回**。ブレる箇所は3箇所に限定され、その3箇所を人間が見るだけで済む。

### 2.2 歩行は8コマではなく4コマでよい（NPC・室内用）

> **プレイヤーの既定は走り**（第6部§4.1・第8部§2.2）。本節の歩き4コマは NPC と室内でのみ使う。

SFC後期RPGの歩行は実質4コマ。多ければ滑らかになるのではなく、**接地の瞬間が正しいと滑らかに見える**。

| コマ | 名前 | 内容 |
|---|---|---|
| 1 | contact | 両足が最も開く。**体が最も低い** |
| 2 | pass | 片足が軸足を追い越す。**体が最も高い**（+1px） |
| 3 | contact（左右反転） | 1の脚を入れ替えたもの |
| 4 | pass（左右反転） | 2の脚を入れ替えたもの |

- コマ3・4は**コマ1・2の脚パーツを入れ替えるだけ**で作れる（新規作画ゼロ）
- **体の上下1pxの揺れ（bob）が滑らかさの9割**を作る。これが無いと「滑っている」ように見える
- 1コマの表示時間: 歩行速度に同期させる。**1歩で進む距離 ÷ 移動速度 = 1コマの時間**。ここがズレると足が地面を擦る
  - 現状は `PLAYER_STEP_DURATION_MS = 253` で1歩を定義済み。この設計自体は正しい

### 2.3 パーツ分解して差分で作る

```
頭（髪＋顔）      … 向きごとに1枚。歩行中は動かさない
胴（服）          … 向きごとに1枚。歩行中は上下1pxだけ動く
腕                … contact / pass の2枚
脚                … contact / pass の2枚
```

これで **1方向あたり実描画6パーツ**、4方向で**実描画は 6 + 6 + 6 = 18パーツ**（西は東の反転）。
40セルを1枚ずつ描くより**桁で速く、原理的にブレない**。

### 2.4 生成AIの正しい使い方

> **生成AIは「下絵を出す道具」であって「素材を出す道具」ではない。**

```
1. 生成AIにマスターポーズの下絵を出させる（大きめ・256px程度で）
2. 人間 or スクリプトが規約に落とす:
   - 目標の高さへ縮小
   - 共有パレットへ量子化（ディザなし）
   - alpha を二値化
   - 輪郭を手で締める（selective outline）
3. 機械ゲートを通す（2.5節）
4. 落ちたら 2 に戻る。生成には戻らない
```

**生成に戻ると絵柄がブレる。** これが07-22の失敗の構造そのもの。

### 2.5 機械ゲート — 契約に追加すべき検査項目

現行契約（寸法・pivot・alpha）に、以下を**追加**する。すべて自動判定できる。

| # | 検査 | 合格条件 | 落ちる理由 |
|---|---|---|---|
| G1 | パレット遵守 | 共有パレット外の色 **0px** | 絵柄ブレの唯一の機械的防波堤 |
| G2 | 色数上限 | 1キャラの使用色 **≤ 16色**（透明含む） | 多色＝滲む＝「不鮮明」 |
| G3 | 部分alpha | 0 < alpha < 255 のピクセル **0px** | すでに実装済み。維持 |
| G4 | 足元pivot | 足裏行が全セルで同一 | すでに実装済み。維持 |
| G5 | シルエット連続性 | 隣接コマのシルエット差分が全体の **25%以下** | これを超えると「別人が交互に出る」＝絵柄ブレ |
| G6 | 顔の可読性 | 顔領域に**背景色でない色が3色以上**、かつ目に相当する暗点が**左右2箇所** | 「顔がない」を落とす |
| G7 | 頭身 | 全高 ÷ 頭部高 が **2.7〜3.2** | 原画実測2.9（第8部 規則6）。7頭身は顔が読めない |
| G8 | 値の分離 | キャラの中央値輝度と、その場所の地面の中央値輝度の差が **25以上** | 背景に溶ける問題 |
| G9 | 孤立ピクセル | 上下左右に同色の隣接を持たないピクセルが **全体の2%以下** | 生成物特有のノイズを落とす |
| G10 | 光源一致 | 左上40%領域の平均輝度 > 右下40%領域の平均輝度 | 光の向きの統一 |

**G1 と G7 と G6 の3つで、7月に起きた失敗はすべて事前に検出できた。**

## 第3章 キャラクターの可読性 — 頭身と色数

07-15「キャラクターも不鮮明で小さい」への回答。

> **確定値は原画実測の 2.9（第8部 規則6、合格範囲 2.7〜3.2）。**
> 本章の表は「なぜ低頭身でないと顔が死ぬか」の理論的背景として残す。表中の「4頭身」推奨は原画到着前の推定であり、採用しない。

### 3.1 可読性は解像度ではなく頭身で決まる

これは直感に反するが、ドット絵制作で最も重要な事実:

> **60pxの高さがあっても7頭身なら顔は読めない。24pxしかなくても3頭身なら顔は読める。**

理由は単純で、顔に使えるピクセル数が違うから。

| 頭身 | 全高60pxのときの頭部 | 顔の描画幅 | 目に使えるpx | 読めるか |
|---|---|---|---|---|
| 7頭身（現状） | 8.5px | **約6px** | 1px×2 | ❌ 読めない |
| 5頭身 | 12px | 約9px | 1px×2 + 間隔 | △ ぎりぎり |
| **4頭身** | 15px | 約11px | **2px×2 + 間隔2px** | ✅ 読める |
| **3頭身** | 20px | 約15px | 2〜3px×2、口も描ける | ✅ よく読める |

**SFC後期RPGはほぼ全部3〜4頭身**である。ロマサガ3のフィールドキャラ、FF6のフィールドキャラ、聖剣3。例外はない。
「リアルな頭身のほうが上等」は完全な誤解で、**この解像度では表情が死ぬ**。

### 3.2 顔の最小仕様

顔幅11px以上を確保したうえで:

```
目    : 2px × 2px の暗点を2つ、間隔2px（＝目の幅の合計6px）
眉    : 目の1px上、1px厚（省略可。感情を出すなら必須）
口    : 1〜2px の暗点（省略可）
鼻    : 描かない（この解像度では汚れになる）
輪郭  : 顔の下側と、光と反対側だけ1px暗く（全周を囲まない）
```

**目は必ず「点」ではなく「2px以上の面」にする。** 1pxの目は縮小・移動で消える。

### 3.3 1体のパレット構成（16色の内訳）

```
肌     3色（明・中・暗）
髪     3色（明・中・暗）
服 主  3色（明・中・暗）
服 副  2色（中・暗）
金具   2色（明・暗）
靴     2色（中・暗）
輪郭   1色（服より暗い、黒ではない）
      ── 計16色
```

**黒（#000000）を輪郭に使わない。** 黒は画面から浮く。「その素材の一番暗い色をさらに暗くした色」を使う。これがSFC後期の質感の核心。

### 3.4 色の作り方 — ヒューシフト

明暗を作るとき、明度だけ動かしてはいけない。**色相も回す**。

```
暗くする → 色相を青/紫方向へ回す + 彩度を上げる
明るくする → 色相を黄/橙方向へ回す + 彩度を下げる
```

例（緑の服）:
```
暗   #2E4A32  (色相 128°)   ← 青寄り
中   #4A7A46  (色相 115°)
明   #8FB562  (色相  85°)   ← 黄寄り
```

これをやらないと、灰色を混ぜたような「濁った絵」になる。現状の素材がまさにそれ。

## 第4章 背景を「生成される仕組み」にする

08-02「美しい背景がマッピングされて生成される仕組み、そのためのアセットの作り方」への回答。

### 4.1 なぜ1枚絵ではだめなのか — 美術ではなく製品の理由

現状の背景は 1586×992 の1枚絵で、`WORLD_WIDTH/HEIGHT` がその実寸に固定されている。
つまり **どのリポジトリを指しても同じ街が出る**。

07-11 の目的「自分の小規模サービスが、RPGの街として立ち上がる」は、**1枚絵では原理的に達成できない**。

> **「美しい背景が生成される仕組み」と「リポジトリごとに街が変わる」は、同じ1つの答えに収束する。**
> それが**タイルとモジュール**である。美術要件と製品要件が一致する唯一の点であり、だからここが本丸。

### 4.2 マスター画像の正しい役割

> **今ある町マスターは「キーアート（完成予想図）」であって「素材」ではない。**

07-22 に決めた「参照画像を提供画像に固定する」は正しい。ただし固定すべきは**色と雰囲気と密度**であって、ピクセルそのものではない。

```
町マスター(1586×992)
  ├─ ここから 抽出 → 共有パレット（32〜48色）        ← 画風の正本
  ├─ ここから 抽出 → 素材ごとの代表パターン           ← タイルの下絵
  └─ そのまま出荷しない（1枚絵はリポジトリを表現できない）
```

**注意（実験済み）**: マスターを機械的に減色するだけでは美しいタイルにならない。
実測: 32色へメディアンカット量子化 → 濁った土色の塊になる。**パレットは抽出値をそのまま使わず、人間/ADが第3章の規則（ヒューシフト・ランプ）で整える必要がある。**

### 4.3 タイルセットの構成

**art pixel = 1、タイル = 16×16px** を基本単位とする。

```
ground/      地面タイル（石畳・土・草・水）  各4バリエーション
edge/        境界タイル（オートタイル用）      各1セット
detail/      散らし（草・ひび・石・落ち葉）   8〜16点
prop/        置物（樽・木箱・看板・花壇）     16〜24点
tree/        樹木                              3種 × 2サイズ
```

#### オートタイル（これが「マッピングされて生成される」の実体）

地面Aと地面Bの境界を、**47種のパターンで自動的に埋める**手法。

```
あるマスの上下左右+斜め、計8方向が「自分と同じ地面か」を調べる
 → 8bit = 256通り、実際に必要なのは 47通り（回転対称を除いた数）
 → その47枚を1セット用意すれば、どんな形の地面でも継ぎ目なく描ける
```

**47枚描けば、無限の形の地面が自動で美しく繋がる。** これが「効率よく」の正体。
実装は `blob tiling` / `47-tile autotile` で検索すれば定番アルゴリズムがある。

#### 建物モジュール

建物は1棟ずつ描かない。**部品にする。**

```
wall_left / wall_mid / wall_right      壁（横に伸ばせる）
roof_left / roof_mid / roof_right      屋根（横に伸ばせる）
door / window / sign / chimney         付属物
```

これで **幅3〜10タイルの建物が、部品10枚で無限に作れる**。
そしてリポジトリのファイル数・モジュール規模を「建物の幅」に写像できる。これが製品の核心。

### 4.4 レイヤー構成

```
L0  ground        地面（オートタイル）              Yソートしない
L1  ground-detail 散らし・影・ひび                  Yソートしない
L2  object        建物・木・置物・キャラ            **足元YでソートしてL2内で並べる**
L3  overhead      屋根・木の上部・橋の上            常にキャラの上
L4  weather       光・霧・パーティクル              加算合成
```

**L2は必ず足元Y座標でソートする。** これが「建物の後ろに回り込める」を作る。
**L3は入室時にフェードする**（第5章）。

### 4.5 決定論的生成

```
seed = SHA-256(リポジトリの正規化fingerprint) の先頭64bit
```
同じリポジトリなら**常に同じ街**が出る。既に `src/town/rng.mjs` と `world-plan-generator.mjs` がこの形になっている。**この資産は生きているので捨てないこと。**

## 第5章 シームレスな入室

### 5.1 仕様

```

```

**これだけ。** 「別フィールドへ移動」ではないから、室内マップも遷移演出も要らない。

### 5.2 気持ちよさを作る細部（これが「お作法」）

| # | 項目 | 数値 |
|---|---|---|
| 1 | フェード時間 | **150ms**（100msだとパチッと切れる、250msだと鈍い） |
| 2 | フェードカーブ | ease-out（最初速く、最後ゆっくり） |
| 3 | ヒステリシス | 入る判定と出る判定の矩形を**4px différent**にする。境界で往復して点滅するのを防ぐ |
| 4 | 音 | フェード開始と同時に扉の軋み1回。フェード完了時ではない |
| 5 | 足音 | 室内に入ったら板張りの音に切り替える |
| 6 | 明度 | 室内は屋外より**わずかに暗く、わずかに暖色**（窓から光が差す表現） |
| 7 | カメラ | 動かさないのが基本。動かすなら**1タイル以内**、200msで |
| 8 | プレイヤー | 屋根が消えている間も**常にプレイヤーが見えている**こと |

## 5. カラー設計

`palette-v1.json` に56色。**全素材はこの中からしか色を取れない**（`PIXEL-ART-BIBLE.md` G1）。

### 5.1 構成

14のランプ × 3〜5段 ＋ `ink #12141C` ＋ `paper #F4EEDC`

```

roofblue 3 / skin 4 / clothwarm 3 / clothcool 3 / gold 3 / lamp 3 / sky 5
```

### 5.2 全ランプが従う規則（ヒューシフト）

```
暗い側 → 色相を青紫へ回す ＋ 彩度を上げる ＋ 明度を下げる
明るい側 → 色相を黄橙へ回す ＋ 彩度を下げる ＋ 明度を上げる
```

例：stone は暗部 H=225°（青）→ 明部 H=40°（黄）。**灰色を混ぜない。**これが濁りを防ぐ唯一の方法。

- **純黒・純白を使わない。** 輪郭は `ink`、最明部は `paper`
- **輪郭は selective outline**。全周を囲まず、光（左上）と反対側だけ

### 5.3 地面のコントラスト規律（モック検証で発見）

> **地面タイル間の輝度差は ±8 以内に収める。**

理由: 地面の明暗が強いと、その上のキャラクターが背景に埋もれる。
実測でこの問題を確認した（レイアウト図パネルA）。地面は**平坦に、キャラは立って**見せる。

### 5.4 キャラクターと地面の分離（G8）

キャラの中央値輝度と、立っている地面の中央値輝度の差が **25以上**。
不足する場合は、キャラ側の主色を1段明るくするか、接地影を1段濃くする。

### 5.5 時刻6段階は「加算レイヤー1枚」で作る

タイルを描き直さない。**全画面に色を1枚重ねる**だけ。

| Lv | 時刻 | 重ねる色 | 合成 | 不透明度 |
|---|---|---|---|---|
| 0 | 朝もや | sky[3] | 通常 | 22% |
| 1 | 明け方 | sky[1] | 乗算 | 30% |
| 2 | 朝 | sky[4] | 通常 | 10% |
| 3 | 昼 | — | — | 0% |
| 4 | 夕方 | roofred[3] | 乗算 | 18% |
| 5 | **黄昏** | gold[0]→roofblue[0] の縦グラデ | 乗算 | 28% |

窓の灯り（lamp）は**加算**で乗せ、Lv3以降で点灯。

### 5.6 気候5変種もパレット差し替えだけ

```

/ 湿潤（foliage濃, water+）/ 霧（全体を sky[2] で12%乗せ）
```

## 7. お作法チェックリスト20（実機で毎回上から確認する）

#### 描画
1. 拡大はニアレストネイバー、倍率は整数
2. 描画座標を整数に丸めてから描く

## 5. 走りの仕様

### 5.1 なぜ走りを既定にするか（実測の結果）

原画1番の歩き6コマ（3列目から8列目）を、4方向すべてで測った結果:

| 向き | シルエット変化率の平均 | 最小 | 頭のてっぺんの上下 |
|---|---|---|---|
| 南（正面） | 22.0% | 10.2% | 187ドット中7ドット＝3.7% |
| 東（横） | 15.3% | 7.5% | 3.7% |
| 西（横） | 13.7% | **3.0%** | 7.0% |
| 北（背面） | 18.5% | 8.0% | 4.3% |

**最小3.0%は、隣り合う2コマがほぼ同じ形だということ。** 動いて見えない。
頭のてっぺんの上下が身長の4〜7%しかない。これでは滑って見える。

歩きは、常にどちらかの足が地面に着いている。だから形の変化幅が構造的に取れない。
走りは、両足が地面から離れるコマがある。だから取れる。

**よってプレイヤーの既定を走りにする。歩きはNPCと室内だけで使う。**

### 5.2 走りの6コマ

| コマ | 名前 | 体の上下（ドット） | 内容 |
|---|---|---|---|
| 1 | 接地・右 | 0 | 右足が着く。前後の足の開きが一番大きい |
| 2 | 沈み | +2（下げる） | 右足に体重が乗る。体が一番低い |
| 3 | 跳ね | −3（上げる） | **両足とも地面から離れる**。体が一番高い |
| 4 | 接地・左 | 0 | コマ1の左右の足を入れ替えたもの |
| 5 | 沈み | +2 | コマ2の入れ替え |
| 6 | 跳ね | −3 | コマ3の入れ替え |

```
1コマの表示時間  66.7ミリ秒（1秒60コマの画面で4コマぶん）
1周期            400ミリ秒
移動の速さ       1秒あたり75ドット
1歩の距離        15ドット
1コマで進む距離  5ドット
体の前傾         頭を足より2〜3ドット前に出す
```

### 5.3 走りの合格の境界

| 項目 | 合格の範囲 |
|---|---|
| シルエット変化率（隣り合うコマ） | **25%以上45%以下**。1組でも外れたら不合格 |
| 同じ形のコマ | **0組**。変化率0%が1組でもあったら不合格 |
| 頭のてっぺんの上下 | 身長の **10%以上**。28ドットの人物なら3ドット以上 |
| 足が地面から離れるコマ | 6コマ中 **2コマ** |
| 接地コマの足の位置 | 1コマ進むごとに、足を画面上で **5ドット後ろへずらす**。ずらさないと足が地面を擦って見える |

### 5.4 歩きの合格の境界（NPC用）

| 項目 | 合格の範囲 |
|---|---|
| コマ数 | 4 |
| 1コマの表示時間 | 133ミリ秒 |
| 移動の速さ | 1秒あたり45ドット |
| シルエット変化率 | **20%以上30%以下** |
| 頭のてっぺんの上下 | 身長の **5%以上** |
| 同じ形のコマ | 0組 |

### 5.5 描く枚数

足の組を3種類（接地・沈み・跳ね）描き、左右を入れ替えて6コマにする。
向きは南・東・北の3方向を描き、西は東を左右反転して作る。

```
足の組  3種類 × 3方向 = 9組
胴と頭  1枚  × 3方向 = 3枚
合計    12枚描けば、走り18コマが作れる
```

## 6. 作業手順

各手順に「やること」「終わったかどうかの確かめ方」「合格の値」を書く。
**確かめ方を実行して合格の値が出るまで、次の手順に進んではいけない。**

#### S1 いま途中になっている変更を片付ける
- **やること**: `git diff` で出る16ファイルの変更を1つずつ見て、残すか捨てるか決める。残すものはコミットする。
- **確かめ方**: `git status --short` を実行する。
- **合格の値**: 何も出力されない。

#### S2 タイルの大きさを決める
- **やること**: 15番のファイルの3段目にある石畳5種類から、模様が繰り返す周期をドット数で測る。その値を16で割った数が、原画を縮める倍率になる。
- **確かめ方**: 測った周期を文書に書き、その倍率で縮めた画像を1枚作って目で見る。
- **合格の値**: 縮めた画像の1タイルが16ドット×16ドットちょうど。

#### S3 パレットを決める
- **やること**: 原画22個から色を集め、物ごと（石・土・草・木・葉・水・屋根・肌・布・金・灯り・空）に暗い順のランプを作る。全部で32色以上48色以下にする。
- **暗い側と明るい側の作り方**: 暗くするときは色味を青や紫の方へ回して鮮やかさを上げる。明るくするときは黄や橙の方へ回して鮮やかさを下げる。灰色を混ぜない。
- **確かめ方**: 色の一覧をJSONファイルに書き出し、色数を数える。
- **合格の値**: 色数が32以上48以下。真っ黒（0,0,0）が0個。真っ白（255,255,255）が0個。各ランプが3色以上。

#### S4 パレットを守らせる検査を作る
- **やること**: 画像を渡すと、S3のパレットに無い色が何個あるかを数えて出すプログラムを書く。
- **確かめ方**: 今出荷中の `public/fable5-v2/assets/characters/player-green-8walk-v4.png` に対して実行する。
- **合格の値**: **不合格が出ること。** 合格が出たら検査が甘いので作り直す。

- **やること**: 建物の入口の四角にプレイヤーが入ったら、キーを押さずに屋根だけを150ミリ秒かけて消し、室内を見せる。出るときは逆。入る判定の四角と出る判定の四角の大きさを4ドット変える。

#### S8 地面のタイルを作る
- **やること**: 15番のファイルから地面5種類と境目20枚を切り出し、S2の倍率で縮め、S3のパレットに置き換える。境目の不足27枚は、既にある20枚を組み合わせて作る。
- **確かめ方**: 47枚すべての組み合わせで隣同士に並べ、境目の1列を比べる。
- **合格の値**: つなぎ目のずれが0ドット。パレットに無い色が0個。

#### S9 建物を左・中・右に切り分ける
- **やること**: 5〜14番の建物を、壁と屋根それぞれ左・中・右に切り分ける。中を繰り返せば横に伸ばせるようにする。
- **確かめ方**: 幅3タイルから10タイルまでの8通りを全部組み立てて画像にする。
- **合格の値**: 8通り全部で、つなぎ目のずれが0ドット、基壇が付いている。

#### S10 街をリポジトリから作る
- **やること**: 対象のリポジトリを調べた結果から、どの建物をどこに置くかを決める。地形と道と区画は、リポジトリの名前だけから決める（中身は使わない）。建物はその区画に入居させる。**空いた区画は更地のまま残す。**
- **確かめ方**:
  1. 同じリポジトリで2回作り、出来た地形と道と区画のデータを比べる。
  2. 同じリポジトリにファイルを1個足して、もう一度作り、地形と道と区画のデータを比べる。
  3. 違う3つのリポジトリで作り、建物の構成を比べる。
- **合格の値**: 1と2は完全に同じ。3は全部違う。
- **これが一番大事**: 2が同じでないと、リポジトリを育てたときに街が組み替わってしまい、「前に空き地だった所に倉庫が建つ」という体験が壊れる。

- **やること**: 22番のファイルの様式を使い、外の業者の申告と町役場の検査を左右に分けて並べる画面を作る。判定の印は4種類（合格・保留・不合格・未検査）。
- **合格の値**: 未検査が不合格と違う色・違う形で出ている。

#### S12 動く物を作る
- **やること**: N3の18コマを作る。灯りの点滅は400ミリ秒と600ミリ秒を交互にする（等間隔にしない）。
- **合格の値**: 画面のどこを見ても、動いている物が常に1個以上ある。

## 7. 完了の決め方

**以下の1つでも欠けていたら、完了と言ってはいけない。**

1. §6のS1からS12まで、全部の「合格の値」が出ている
2. ブラウザで人が実際に一周できる
3. `npm run check` を実行して、エラーで止まらない
4. `git status --short` が何も出力しない

**言ってはいけない報告の例**:
- 「テストが通ったので完了しました」→ 2が無い
- 「実装は完了しています」→ 動かして確かめていない
- 「暫定的に対応しました」→ 未完成を完成に見せている
- 「ほぼ完了しました」→ 完了か未完了かのどちらかしかない

**合格の値が出せないときの正しい報告**:
```
S5 の頭身が 3.4 で、合格の範囲（2.7〜3.2）に入っていません。
頭を1ドット大きくして測り直します。
```
数値で言う。範囲を書き換えて合格にしない。

## 15.1 クエスト設計 — 調査ループの中身

### 15.1.1 いまの実装が既に持っている核

現行の宿屋ループは「手掛かりを調べ、**観測した／推定できる／わからない** の三択を選ぶ」遊びである。
これは所有者の原則「**観測・推定・不明を分けて示す。未検査は故障ではない**」（`AGENTS.md`）の遊戯化であり、
**この三択は本製品の発明である。捨ててはいけない。** 捨てるのは据え置きの文言だけ。

### 15.1.2 依頼の生成規則

```
1. /api/town の検出結果から、証拠分類が「推定」または「不明」の事実を集める
2. 住める街の判定に影響する順に並べる（入口 > 台帳 > 井戸 > 検査 > 見張り > 修理）
3. 上位3件を調査地点にする
4. 3件に満たないときは「汚れ」（廃屋・草むら＝legacy/TODO）から補う
```

**調査地点は必ず、その事実に対応する施設の前に置く**（第6部§6.2の言い換え表と同じ対応）:

| 事実 | 地点 | 目印（原画19番） |
|---|---|---|
| 入口が不明 | 城門・宿屋の前 | 足跡と虫眼鏡 |
| 台帳が不明 | 倉庫の予定地（更地） | 足跡と虫眼鏡 |
| 井戸の水が不明 | 井戸端 | 同 |
| 検査台が不明 | 道場の前 | 同 |
| 夜の記録が不明 | 見張り台の下 | 同 |
| 由来不明の物 | 廃屋・草むら | 同 |

### 15.1.3 地点での行為

```
1. 近づくと目印が見える（キー入力なしで気づける）
2. Enter で調べる → その場の様子が2行以内で出る
3. 三択を選ぶ:  「見た」（観測） / 「そうらしい」（推定） / 「わからない」（不明）
4. 選んだ結果が記録に残り、掲示板の札の文面に反映される
```

**正解は無い。** 記録の正直さが目的で、当てるゲームではない。だから間違いの罰も無い。

### 15.1.4 話法の三分類（全NPC・全札に適用する文法）

証拠分類を、**文末で**示す。画面に「観測」「推定」という語を出さない。

| 分類 | 文末 | 例 |
|---|---|---|
| 観測 | 断定「〜です」「〜ます」 | 倉庫は空き地です。 |
| 推定 | 「〜のようです」「〜らしいです」 | 水は湧いているようです。 |
| 不明 | 「まだ、わかりません」 | 夜のことは、まだわかりません。 |

**合格の境界**: 観測でない事実を断定形で書いた文が0件。機械検査可能（事実の分類と文末の対応表を照合する）。

### 15.1.5 報告と完了

報告は役場（役場が閉鎖中の間は掲示板の書記）。報告すると:
1. 書記が札を貼り直す（第6部§3.6の様式2）
2. 確定した事実に対応する施設の見た目が変わる（第15.3の表）
3. 次の依頼は**再訪時に差分から**生成する。同じセッション内で連続発行しない（切りの良い去り際を作る）

## 15.3 報酬の定義 — 観測された変化だけが報酬

所有者の原文（07-11）:
> 実際に報酬になるのは、次のような観測された変化だけ。

これを画面の変化に1対1で割り当てる。**この表に無い報酬を追加してはいけない**（点数・実績・通貨を作らない）:

| 観測された変化 | 街で起きること |
|---|---|
| build が通った | 工房の炉に火が入り、煙突から煙 |
| local run できた | 街に通電し、時刻が Lv.1 の明け方へ |
| 宿屋に灯りがついた（公開URLが応答した） | 宿屋の窓が点く。宿帳係が立つ |
| 旅人が受付まで来た（実アクセスの記録） | 宿の前に旅人モブが1体増える |
| 酒場で注文が通った（外部API疎通） | 酒場の杯が動き、ざわめきが増す |
| 船着場から船が出た（リリース／配布） | 出港の演出。桟橋に荷が積まれる |
| 見張り台がログを記録した | 見張り台の灯りが点く |
| 道場の検査を通った | 検査済の印章（原画22番）が報告書に押される |
| rollback 手段が確認された | 修理小屋に道具が掛かる |

**自己申告は報酬にしない。** 外部工務店の報告は、役場に綴じられ検査印欄が空欄のまま（15.4）。

## 15.4 役場の工事報告 — 「作らせた人」のための機能

3人目の顧客（LLMに書かせて中身を知らない人）が最も必要としているのは**「誰が何を建てたかの台帳」**である。

```
1. git の履歴から、共同署名（Co-Authored-By: Claude 〜 / Codex 〜 等）付きの変更を検出する
2. それを役場の「工事報告」として綴じる。1件 = 原画22番の様式2（自己申告と公式検査の左右分離）
3. 左（自己申告）: 変更の要約・日付・工務店名
4. 右（公式検査）: 対応する検査の結果。**検査が無ければ未検査の灰丸のまま**
5. 門の外の代理人（第5部§9）の台詞は、この未検査件数と連動する
```

**これで「Claude Code / Codex の自己申告しかない」状態が、歩いて見える台帳になる。**

## 15.5 アセットのライフサイクルと置き場所

所有者の事業部制（07-29）に従い、**4,654点の全部がこの経路を通る**:

```
1. 候補     studio/art-department/candidates/<資産キー>/   ← 生成・作画の出力先
2. 検収     studio/quality/gates/ の検査（第9部§2.3 G1〜G10・C1〜C6）で数値合格
3. 承認     studio/governance/approvals/ に記録。**昇格できるのは人間の所有者だけ**（AGENTS.md）
4. 正本     studio/art-department/masters/ に確定版を置く
5. 出荷     ship/50-art/<分類>/ へ複製し、manifest に記載して初めてゲームが読む
```

- **命名**: `<分類>_<名前>_<動き>_v<番号>.png` 例: `char_innkeeper_run_v1.png` / `tile_cobble_blob47_v1.png`
- **manifest 記載事項**: 資産ID / 出荷先URL / 由来原画のファイル名 / ハッシュ値 / 検査結果の数値
- 既存の `assets/prefabs/manifest.json`（48点で実績）の形式を引き継ぐ
- **studio/ は出荷後に消してよい**（所有者の定義）。ship/ に無いものは顧客に届かない

## 15.6 性能の予算

| 項目 | 予算 | 測り方 |
|---|---|---|
| 街の生成（1000ファイルのリポジトリ） | **2秒以内** | 既存テストの上限を9.2秒の実測から引き下げる |
| 描画 | 1コマ **16ミリ秒以内**（60コマ/秒） | ブラウザの計測タブで1分間歩いて最悪値を取る |
| 起動から操作可能まで | **3秒以内**（演出2.8秒＋余白） | 実測 |
| 出荷する画像の合計 | **10MB以下** | ship/50-art の合計サイズ |
| 保存データ | 1リポジトリあたり **64KB以下** | localStorage の実測 |
